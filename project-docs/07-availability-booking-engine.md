# Availability & Booking Engine — V1 (Minimal)

Per Option B: real in-app booking and payment stay in V1, but the engine is deliberately minimal — no recurrence, no dynamic pricing, no resource partitioning, no configurable buffer time. What cannot be cut: preventing two people from booking the same slot.

## Data
- `slots` table: `resource_id, start_time, end_time, status (open/held/booked), hold_token_hash, held_by_user_id, held_until, payment_intent_ref, version`. Unique `(resource_id, start_time, end_time)` prevents duplicate generated slots.
- Slots are generated by a scheduled job over a rolling window (e.g. next 30–90 days) based on `operating_hours` — not pre-generated forever.
- Generation uses facility IANA timezone plus `operating_hour_exceptions`; define overnight hours and DST behavior before launch.
- Generate slots from local facility wall-clock times using IANA timezone. `close_time < open_time` means close next local day; nonexistent DST times are skipped; ambiguous DST times use earlier offset. Resource `slot_duration_minutes` must be positive and divide each generated operating interval.

## Booking flow
1. Client requests to book a slot with idempotency key.
2. Server opens a DB transaction, runs `SELECT ... FOR UPDATE` on the target slot row.
3. Check `status = 'open'`. If not, reject immediately (already held/booked).
4. Create `bookings` row with `pending_payment` status and immutable price/policy snapshot, then create one pending `payments` attempt. Set slot `status = 'held'`, create cryptographically random hold token, store only its hash with user ID, payment attempt ID, and short expiry (~5 minutes), then commit. Create provider payment intent using payment attempt's provider idempotency key; store returned provider reference only on payment attempt. Return raw hold token only to client/payment workflow.
5. Client completes payment against the held slot.
6. On payment success, verified provider webhook resolves payment attempt by provider reference, locks linked slot; it must match hold owner and unexpired held state before flipping slot to `'booked'`, confirming existing booking, writing immutable financial ledger entries, and emitting `booking.confirmed`. Persist webhook event ID for idempotency.
7. On payment failure or timeout, scheduled job finds expired `'held'` slots, flips them back to `'open'`, and marks matching `pending_payment` booking `expired` in same transaction.
8. An authorized staff member may block an open slot, recording blocker and reason. Customer cancellation records policy result; it releases slot only when policy permits rebooking.

Payment-intent creation is retried by a reconciler using the same provider idempotency key after crashes or timeouts. If intent creation remains unavailable until hold expiry, expire booking, release slot, and cancel any created intent. Webhook processing remains safe when it arrives after expiry; it creates an exception/refund workflow and never confirms expired booking.

## State and closure rules

- Slot: `open -> held -> booked`; `held -> open` only on expiry/payment failure/release; `open -> blocked -> open` only through authorized staff action. No other transition is valid.
- Booking: `pending_payment -> confirmed|expired|cancelled`; `confirmed -> cancelled|no_show`; terminal states never return to active. Payment/refund state remains on payment records.
- Payment: `pending -> succeeded|failed`; a successful capture may later be refunded/partially refunded, never return to pending. Refund: `pending -> succeeded|failed`. Payout: `pending -> paid|failed`.
- Resource block or operating-hour exception changes future `open` slots to `blocked`. It does not silently alter held or confirmed bookings. Held slots are released only after payment-intent cancellation; confirmed bookings require explicit staff/admin cancellation, customer notification, and refund decision.
- Facility suspension prevents new holds. Existing confirmed bookings stay valid unless platform administrator performs documented cancellation workflow.

## Why this is safe under concurrency
- The row lock (`FOR UPDATE`) means two simultaneous booking attempts on the same slot serialize — the second one sees `status != 'open'` and is rejected cleanly, not double-booked.
- The `version` column is backup optimistic-lock mechanism. Any non-locking update must include `WHERE version = :expected_version` and increment version.
- Idempotency keys on the booking-create endpoint prevent a retried request (network blip, double-tap) from creating a second booking for the same intent.
- Active-booking partial uniqueness permits only one pending/confirmed/no-show booking per slot, while preserving cancelled/expired history and allowing rebooking.

## Interface boundary (for future extensibility)
Expose exactly three methods and keep all callers using only these:
- `AvailabilityService.holdSlot(resourceId, slotId, userId, idempotencyKey)` returns hold token and expiry
- `AvailabilityService.confirmSlot(slotId, holdToken, paymentIntentRef)`
- `AvailabilityService.releaseSlot(slotId, holdToken)`

When the engine grows later (recurring bookings, buffer time, resource partitioning, possibly extracted into a dedicated Go service under load), the implementation behind these three methods changes — not the modules that call them.
